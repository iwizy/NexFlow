# 0.1 Candidate Scope

Status: Frozen and evaluated for `v0.1.0-rc.1`

This document defines the feature boundary used to evaluate NexFlow
`v0.1.0-rc.1`. It freezes scope; it does not accept every draft RFC, change
manifest `specVersion`, or imply a stable specification or runtime.

The candidate remains a specification-first repository snapshot. Its useful
implemented surfaces are schemas, examples, profiles, fixtures, and repository
validation checks. It does not contain a reference CLI, runtime, provider
adapter, extension loader, live integration, or orchestration engine.

## What The Freeze Means

The `0.1` candidate review is limited to the surfaces in this document. Until a
candidate decision is recorded:

- no new core manifest kind may enter the `0.1` baseline
- no new required top-level manifest field may enter the baseline
- no optional or experimental surface may be promoted into the core baseline
- no new authority, permission, approval, context, memory, network, or runtime
  behavior may become an implicit default
- no documentation may imply that policy is enforced or work is executed
- corrections may resolve contradictions, validation failures, unsafe
  ambiguity, broken links, inaccurate status claims, or missing migration notes
- evidence, examples, and non-normative clarification may improve without
  widening the supported feature boundary

A proposed scope expansion requires a written compatibility and safety review,
an RFC when governance requires one, synchronized documentation and evidence,
and an explicit decision to reopen the freeze. The readiness review must then
be rerun against a new exact commit.

## Status Axes

NexFlow keeps candidate treatment separate from implementation evidence and RFC
stage. Combining those concepts would make a schema look like runtime support
or make an implemented slice look like an accepted RFC.

### Candidate Treatment

| Treatment | Meaning for `0.1` |
| --- | --- |
| **Baseline** | Included in the candidate review and supported as draft authoring or repository-maintenance surface. |
| **Optional** | May ship in the repository, but is not required for Core Profile authoring or candidate readiness. |
| **Migration-only** | Preserved only so existing draft manifests can move to the preferred form. New manifests should not adopt it. |
| **Deferred** | Explicitly outside the `0.1` candidate boundary. |

### Evidence Status

The [Compatibility Matrix](compatibility-matrix.md) remains authoritative for
evidence claims:

- **Implemented** means a repository artifact exists and is exercised by a
  documented check.
- **Partial** means only a bounded subset is implemented.
- **Specified** means documentation defines the intended contract without a
  complete implementation.
- **Planned** means the surface is future work.

RFC stages remain those recorded in the [RFC Index](../rfcs/README.md). A Draft
RFC may have an implemented slice. That does not make the whole RFC Accepted.

it does not mean every kind is required by the Core Profile or enforced by a
runtime.

| `AgentSet` | Baseline | Implemented | Stable AI identity and legacy participant compatibility; duplicated effective behavior fields are migration-only. |
| `AgentDefinitionSet` | Baseline | Implemented | Versioned requested behavior and unique unscoped active-definition authority; no agent execution. |
| `Workflow` | Baseline | Implemented | Declarative stages, steps, dependencies, gates, and event references; no scheduling or execution. |
| `TaskSet` | Baseline | Implemented | Declarative work, dependencies, artifacts, and acceptance criteria; no task engine. |
| `HandoffSet` | Baseline | Implemented | Structured responsibility transfer declarations; no messaging or state synchronization. |
| `CapabilitySet` | Baseline | Implemented | Technical action vocabulary; capability does not grant permission. |
| `PermissionSet` | Baseline | Implemented | Allow, deny, and approval-required declarations; no runtime enforcement. |
| `ContextSet` | Baseline | Implemented | Declared sources and access boundaries; no connector, retrieval, or credential access. |
| `MemorySet` | Baseline | Implemented | Retention, ownership, visibility, sensitivity, and consumer declarations; no memory store. |
| `ProviderSet` | Baseline | Implemented | Provider-neutral features and constraints; no live provider facts, selection, or calls. |
| `ModelProfileSet` | Baseline | Implemented | Requested provider-neutral model selection and fallback declarations; no model resolution. |

## Migration-Only Surface

The following forms remain structurally valid only for migration compatibility:

- duplicated AgentSet behavior and access fields, replaced by authoritative
  AgentDefinitionSet configuration
- ProviderSet `capabilities`, replaced by provider `features`
- provider `allowTrainingUse`, replaced by explicit `trainingUse`
- approval gate scalar `appliesTo`, replaced by typed `targets`

A candidate must preserve their documented non-authoritative meaning and link
to migration guidance. A future removal requires a version and compatibility
decision.

## Deferred Without Blocking `0.1`

The following work is useful but not required for the frozen candidate:

- an independently published schema package, canonical schema URI policy, and
  checksum distribution; a repository tag or commit identifies the `0.1`
  snapshot
- a stricter opt-in schema profile and broader positive or negative fixtures
- complete semantic validation, stable diagnostic codes, graph safety checks,
  and policy-consistency validation
- a machine-readable Agent Assembly output format or resolver
- broader ActorSet and active-definition migration across every example
- live CloudEvents or OpenTelemetry export and import
- extension registries, loaders, protocol clients, and live integrations
- the reference CLI, runtime architecture decision, runtime, provider adapters,
  orchestration, deployment, and production enforcement

Deferring these items is not evidence that they are safe or specified enough
to implement. It only means the `0.1` candidate does not depend on them.

Draft RFCs are not automatically blockers. They block a candidate only when
their current treatment is missing, contradictory, unsafe, or relied upon as an
implemented contract beyond the boundary above.

## Candidate Decision Rule

A maintainer may record `ready` or `ready-with-notes` only when:

1. the evaluated commit matches this frozen scope or an explicitly reviewed
   successor
2. every machine-readable readiness gate is `passed` or `not-applicable`
3. no unresolved blocker remains
4. validation and compatibility evidence identify the exact commit
5. draft, experimental, migration-only, and deferred surfaces remain visibly
   separated from implemented runtime claims
6. the release notes state that `0.1` is a draft specification candidate

Tagging a candidate does not change manifest `specVersion`, accept every RFC,
or authorize runtime implementation. Any of those actions requires its own
decision.
