# 0.4 Alpha Preparation Checkpoint

- Checkpoint date: 2026-09-12
- Checkpoint state: **prepared with blockers**
- Release decision: **not ready**

This checkpoint evaluates whether the current NexFlow repository can support a
reference CLI alpha release. It records evidence and blockers; it does not
publish an alpha, approve a tag, select an implementation language, or create
an `NF-CLI` conformance claim.

## Version Line Boundary

The public [Release Plan](release-plan.md) assigns different outcomes to the
two relevant version lines:

- `0.4` is Runtime Architecture Decision readiness
- `0.5` is a possible reference tooling preview

The phrase "0.4 alpha checkpoint" is therefore a preparation label, not a new
public version promise. A future CLI alpha version remains `TBD` until the
project accepts an architecture decision and explicitly reconciles the
repository release line with the independently versioned CLI package.

This checkpoint does not change:

- the released NexFlow repository baseline, `v0.1.0`
- manifest `specVersion: "0.1"`
- the prototype JSON `formatVersion: "0.4-draft"`
- RFC-0011's Draft status
- the Runtime Architecture Decision review outcome of `not-ready`

Those are separate version and decision domains. Similar numbers do not make
them interchangeable.

## Assessment Vocabulary

| State | Meaning |
| --- | --- |
| `ready` | The gate has sufficient reviewed evidence for this checkpoint. |
| `partial` | Useful evidence exists, but it does not cover the complete release surface. |
| `blocked` | A required upstream decision or contract prevents completion. |
| `not-started` | Required release evidence or ownership has not been produced. |

Only an assessment with every mandatory gate at `ready` may proceed to an
alpha release decision. `Partial` is evidence, not approval.

The mandatory gate result is `not-ready`. The repository has meaningful
prototype evidence, but no accepted architecture, stable public CLI contract,
installable artifact, or release-bound conformance record.

## Runnable Evidence

The current evidence is intentionally executed from a repository checkout:

```sh
npm ci --ignore-scripts
npm run validate
npm run cli-prototype -- --help
npm run cli-prototype -- validate --root examples/minimal-team
npm run cli-prototype -- inspect --root examples/minimal-team
npm run cli-prototype -- graph --root examples/minimal-team
```

The complete CLI regression suite is:

```sh
npm run cli-prototype-smoke
npm run cli-validation-smoke
npm run cli-diagnostics-smoke
npm run cli-inspection-smoke
npm run cli-graph-smoke
npm run cli-init-smoke
npm run cli-no-runtime-guardrails-smoke
npm run cli-fixture-smoke
```

These commands support statements about the checked repository revision. They
do not verify an installer, public package, binary, supported-platform matrix,
upgrade path, or independently consumable CLI artifact.

## Claim Ceiling

At this checkpoint, maintainers may state that NexFlow has:

- a documented validation-only reference CLI target
- runnable repository evidence for bounded validation, inspection, graphing,
  and initialization
- versioned experimental JSON diagnostics
- fixture and CI coverage for the repository prototype
- explicit no-runtime boundaries and regression guardrails

Maintainers must not state that NexFlow has:

- released a reference CLI alpha
- selected JavaScript or any other runtime language
- published a supported `nexflow` package or executable
- implemented complete semantic validation
- satisfied `NF-CLI` conformance
- provided an operating-system sandbox
- authorized workflow, provider, integration, credential, approval, or
  deployment effects

## Blocker Closure Sequence

1. Publish and review the Runtime Architecture Decision proposal against the
   existing mandatory gates.
2. Complete comparable candidate evidence and accept one exact architecture,
   package layout, target matrix, and ownership model.
3. Accept the reference CLI scope and reconcile the `0.4` and `0.5` release
   language with the independently versioned CLI package.
4. Freeze the alpha command grammar, discovery rules, structural and semantic
   coverage, diagnostics, output version, and compatibility commitments.
5. Define the exact `NF-CLI` claim, evidence ownership, and unsupported-feature
   treatment, or explicitly release without a conformance claim.
6. Build installable candidate artifacts and record source revision,
   checksums, provenance, signing status, supported platforms, and runtime
   prerequisites.
7. Run repository and artifact-level suites against the exact candidate on
   every supported platform, including no-runtime boundary checks.
8. Complete independent documentation, security, compatibility, and release
   review; then replace all placeholders in the release notes.
9. Record a separate release decision before creating or announcing a tag.

Steps may produce evidence in parallel, but no downstream artifact may be used
to bypass an unresolved upstream decision.

## Reassessment Triggers

Re-run this checkpoint when any of the following occurs:

- the Runtime Architecture Decision outcome changes
- RFC-0011 changes status or public command scope
- package layout, implementation language, or supported platforms are selected
- the prototype is promoted, replaced, or begins sharing code with a runtime
- diagnostic or manifest compatibility changes
- a candidate distribution artifact is produced
- an `NF-CLI` conformance scope is proposed

Every reassessment must identify the exact candidate revision and evidence
runs. A prior `ready` gate returns to `partial` or `blocked` when its underlying
contract changes without replacement evidence.

## Checkpoint Decision

The `0.4` alpha preparation checkpoint is **prepared but not passed**. Continue
specification, architecture, test, and release-evidence work. Do not publish a
CLI alpha, change the public version, or send the draft release announcement
until a separate candidate review closes every mandatory gate.
