   decision and complete the separate `0.4` milestone review first.
2. Accept the public CLI scope, package boundary, version mapping, supported
   platforms and release/security ownership. Explicitly select alpha/beta
   treatment without skipping the applicable alpha publication gates.
3. Freeze command, schema, diagnostic, compatibility and conformance
   boundaries. Replace or promote experimental source tooling only under the
   accepted decision.
4. Produce installable candidate bytes and their digests, provenance and
   signing record. Verify clean installation, usage, failures, upgrade,
   rollback and uninstall on each supported platform.
5. Assemble a fresh candidate-bound B1–B8 record and complete independent
   security, documentation, compatibility and release review. A maintainer
   must separately authorize any tag, package, announcement or support claim.

These are next actions, not authorization to execute additional tasks. A
remaining `partial`, `blocked` or `not-evaluated` mandatory gate prevents beta
publication approval.

Reassess when the architecture/RFC status, candidate source, public scope,
version mapping, artifacts, dependency graph, target matrix, security findings,

failed evidence; identify its replacement rather than silently upgrading a
gate. Planning dates, PR merges and green CI are not release decisions.
