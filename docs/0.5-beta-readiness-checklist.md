# 0.5 Reference Tooling Beta Readiness Checklist

Status: prepared checklist; no beta candidate has been evaluated or approved.

The [2026-10-03 beta preparation checkpoint](0.5-beta-checkpoint.md) records an
eight-gate source assessment with outcome `not-ready`. It is not an evaluated
installable beta candidate or an approval of this checklist's release gates.

This checklist is for a possible validation-focused reference tooling beta on
the [`0.5` line](release-plan.md#05-reference-tooling-preview). It defines what
reviewers must inspect; it is not a release announcement, a schedule, a tag
proposal, or evidence that a reference CLI exists. The earlier
[alpha preparation checkpoint](0.4-alpha-checkpoint.md) remains `not-ready`.
The [source-checkout dry run](cli-release-dry-run.md) can supply preliminary
evidence, but cannot substitute for testing installable candidate artifacts.

The public repository release, CLI package, manifest `specVersion`, schema
artifact, diagnostic output format, and conformance claim have independent
versions. A beta label for any one of them does not advance the others. If a
beta is proposed before an alpha has been published, reviewers must justify
that label and still close every applicable alpha publication gate in the
[draft release notes](cli-alpha-release-notes.md#publication-readiness).

## Candidate Record

Create a separate, reviewable record for one candidate. Do not fill these
fields from a moving branch name or copy a prior green run without checking
its tested revision.

| Field | Record before evaluation |
| --- | --- |
| Candidate purpose and proposed beta label | Not selected |
| Exact source commit and proposed repository tag | Not selected |
| CLI package name, version, and distribution channel | Not selected |
| Manifest `specVersion` range and schema snapshot or artifact revision | Not selected |
| Diagnostic/output format version and compatibility policy | Not selected |
| Supported platforms and runtime prerequisites | Not selected |
| Artifact filenames, digests, provenance, and signing status | Not available |
| CI runs, clean-install runs, and security review | Not evaluated |
| Release owner, security owner, reviewers, and decision time | Not assigned |
| Open blockers, limitations, and release decision | Not evaluated |

Use `not-evaluated`, `ready`, `partial`, `blocked`, or `not-applicable` for each
gate below. `Ready` requires evidence tied to the candidate source and
artifact. `Partial` is not approval. `Not-applicable` requires a reason and
cannot be used to avoid a mandatory release boundary. A failed or superseded
run remains visible with its revision and replacement evidence.

## B1 — Decisions, Ownership, And Version Mapping

- [ ] An accepted, revision-pinned Runtime Architecture Decision supports the
  CLI implementation language, package layout, shared-library boundary,
  supported platforms, and ownership model. The existing `not-ready` review
  is not treated as acceptance.
- [ ] The reference CLI scope has completed the RFC process; supported
  commands, filesystem effects, and exclusion of runtime behavior are frozen
  for this candidate.
- [ ] Maintainers explicitly decide whether this is a repository `0.5` beta,
  a separately versioned CLI package beta, both, or neither. The tag, package
  version, manifest `specVersion`, schema artifact version, and diagnostic
  format are recorded independently.
- [ ] A release owner and security owner accept the support, correction,
  withdrawal, and incident-response responsibilities for the proposed beta.

## B2 — Supported Command And Validation Surface

- [ ] Candidate help, documentation, and tests agree on the exact public
  `validate`, `inspect`, `graph`, and optional `init` command grammar, inputs,
  outputs, exit statuses, and unsupported cases.
- [ ] `validate` parses supported local inputs, selects the pinned schema
  snapshot, rejects unsupported versions and kinds clearly, and documents
  which syntax, structural, semantic, and policy checks are actually run.
- [ ] `inspect` produces useful bounded human output and a documented machine
  representation without presenting declarations as resolved authority or
  exposing arbitrary manifest values.
- [ ] `graph` remains an explanatory static projection; it does not schedule,
  execute, authorize, or imply complete semantic graph validation.
- [ ] If `init` is included, it writes only to an explicit destination,
  documents its exact file budget, refuses conflicting targets without partial
  overwrite, and does not initialize credentials or a runtime.
- [ ] Positive, negative, unsupported, and malformed-input fixtures exercise
  every supported command and the published compatibility boundary.

## B3 — Schemas, Diagnostics, And Conformance

- [ ] Schema distribution has the reviewed immutable, language-neutral
  [bundle contract](schema-bundle-publication.md): version separation,
  inventory, integrity, reproducibility, and offline consumer verification.
  If a bundle is distributed with this beta, verify the actual artifact too.
- [ ] The exact schema snapshot and supported manifest kinds and profiles are
  named; structural success is not represented as complete semantic validity,
  Core Profile closure, policy enforcement, or execution safety.
- [ ] Diagnostic categories, safe locations, ordering, truncation, severity,
  exit statuses, and machine-output format are documented and tested. Any
  incompatible format change has versioning and migration guidance.
- [ ] An explicit conformance decision identifies either a candidate-bound,
  evidence-backed `NF-CLI` claim or the absence of such a claim. The
  [draft repository-validator statement](../conformance/REPOSITORY-VALIDATOR-CLAIM.md)
  is not reused as CLI evidence or certification.

## B4 — No-Runtime And Security Boundary

- [ ] Validation and inspection run without provider calls, credentials,
  executable extensions, runtime services, hidden remote checks, task
  execution, approval enforcement, or deployment effects.
- [ ] Command-specific filesystem, network, process, credential, extension,
  and remote-system effects match the [CLI/runtime boundary](cli-runtime-boundary.md)
  and are covered by failure as well as success tests.
- [ ] Inputs and diagnostics do not disclose secrets, raw untrusted values,
  local absolute paths, or unsafe terminal text beyond reviewed allowlists.
- [ ] Dependency and supply-chain findings have a dated assessment and
  disposition; unresolved high-impact findings are release blockers unless
  maintainers record an explicit, justified exception under project policy.
- [ ] Security reviewers distinguish application-level guardrails from an
  operating-system sandbox and record residual risks honestly.

## B5 — Installable Artifacts And Provenance

- [ ] Each proposed beta artifact installs from its documented public
  distribution channel in a clean environment without relying on a source
  checkout or unpublished local files.
- [ ] The artifact identifies its own package version, source commit,
  supported platforms, runtime prerequisites, license, and maintainer; it
  does not borrow a manifest or repository version as its package identity.
- [ ] Digests, provenance, and signing status are recorded for the exact
  downloadable bytes. The release notes explain any missing integrity or
  signing control rather than implying it exists.
- [ ] A clean install, help/version check, representative validation and
  inspection, failure case, upgrade path, and uninstall path pass against
  those exact bytes on every supported platform.

## B6 — Reproducible Verification

- [ ] The complete repository checks pass on the exact candidate commit,
  including schema/example validation, negative fixtures, conformance-claim
  checks, documentation navigation, semantic smoke checks, and the dedicated
  CLI regression suite.
- [ ] CI run URLs, conclusions, checked commit identities, tool versions, and
  environments are recorded. A synthetic pull-request merge commit is not
  silently substituted for the proposed release commit.
- [ ] Artifact-level tests repeat the public install and quick start from
  clean environments on every supported platform; source-checkout smoke
  results alone do not mark this gate ready.
- [ ] Release evidence records the result of every required check, including
  failures and reruns, and is attached to an immutable candidate revision.

## B7 — Compatibility, Documentation, And Support

- [ ] README, release notes, installation guide, help text, compatibility
  matrix, schema guide, validation guide, changelog, and known limitations
  agree with the actual candidate behavior and artifact.
- [ ] Supported versions, profiles, commands, platforms, output contracts,
  deprecations, and migration or rollback steps are explicit. Existing
  projects and prior tool outputs are tested where compatibility is claimed.
- [ ] Documentation separates implemented, partial, specified, planned, and
  unsupported behavior; it does not call the repository prototype a released
  reference CLI or describe schema validity as runtime approval.
- [ ] Public feedback, issue triage, security reporting, support window, and
  beta correction or withdrawal routes are documented and owned.

## B8 — Independent Review And Publication Decision

- [ ] Reviewers compare the exact source commit, artifact digests, CI runs,
  security assessment, conformance decision, documentation, and release notes
  as one candidate. Each blocker has factual closure evidence.
- [ ] The review record names its decision makers, time, gate states,
  unresolved limitations, dissent, and rationale. Every mandatory B1–B7 gate
  is `ready`; a remaining `partial`, `blocked`, or `not-evaluated` gate prevents
  publication approval.
- [ ] Maintainers make a separate explicit release decision before creating
  any beta tag, package, announcement, badge, or support claim.

After an approved publication, verify the tag, downloadable artifacts,
digests, installation instructions, release links, and public status from a
clean environment. Record any rollback or correction required. This is a
post-publication check, not a condition that can be completed before the tag.

## Preparation Context And Handoff

At checklist preparation, the [alpha checkpoint](0.4-alpha-checkpoint.md)
records `not-ready`; the [alpha notes](cli-alpha-release-notes.md) are blocked
drafts; the current [repository prototype](cli-prototype.md) is not an
installable reference CLI; and the [validator statement](../conformance/REPOSITORY-VALIDATOR-CLAIM.md)
is a draft, narrow `NF-SCHEMA` claim, not `NF-CLI` evidence. These facts are
starting context, not a gate-by-gate beta assessment.

A later checkpoint should create the candidate record, assign every B1–B8
gate a state and evidence, and identify the next blocker-closing action. Do
not mark this checklist complete merely because it exists, a dry run passes,
or a documentation PR merges.
