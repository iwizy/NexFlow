# 0.5 Reference CLI Preview Contract

Status: adopted implementation profile for NF-104, reviewed on 2026-10-28.
This document freezes the first preview's scope; the packages and commands below
are implementation targets, not available downloads. The
[scope review](../rfcs/reviews/2026-10-28-cli-preview-scope.md) records its exact
inputs and delegated decision. The broader RFC-0011 remains Draft.

## Product And Package Boundary

The accepted TypeScript/layout B direction in
[RFC-0025](../rfcs/RFC-0025-reference-implementation-architecture.md) applies.
Implement two packages, without creating future host or adapter implementations:

| Package | Responsibility | Permitted imports and effects |
| --- | --- | --- |
| `@nexflow/validation` | Pure parsing, pinned local schemas, implemented static checks, safe diagnostic and declared inspection/projection data | Its own pure dependencies and immutable specification data; no filesystem, network, process, credential or runtime constructors, including on import. |
| `@nexflow/cli` | Argument parsing, root-bound workspace reads, human/JSON presentation and static graph projection | Validation package and bounded local read adapter; no host, provider, executable-extension, credential or runtime initialization. |

These are package identities for local tarball installation; no public registry
namespace is claimed or reserved. The CLI has the `nexflow` bin entry. Its
matching validation package and complete runtime dependency closure must be
included in the CLI tarball so installation needs neither a source checkout nor
a registry lookup. NF-107 must verify actual tarball bytes and offline install
with an empty cache; a clean npm install that downloads dependencies is not that
verification. Install/build scripts from dependencies remain disabled.

The validation package exposes one main pure API; the workspace adapter belongs
to the CLI and is not a hidden filesystem-capable validation export. No future
host API/ABI is released with this preview. Experimental library entries remain
experimental, and neither those sources nor the historical JavaScript CLI are
renamed into a finished product.

that the unbuilt packages pass on it. No other Node version is supported by this
preview contract until separately qualified. The older evaluation Node 26.12.0
and private maintenance `engines` field do not establish public support.

Required native targets are Ubuntu 24.04 AMD64, macOS 15 ARM64 and Windows Server
2025 AMD64. NF-109 records actual OS/image/CPU/runtime fingerprints and every
claimed target result. A changed hosted image is disclosed; emulation or a local
macOS release cannot substitute. Build pins/locks are chosen from the reviewed
TypeScript baseline in NF-105 and checked as actual supply-chain inputs in
NF-108; this scope decision changes no lockfile or runtime installation.

No beta label or stable `0.5.0` publication is implied. Future patches use a new
preview identifier and migration note when public grammar, diagnostics or API
changes incompatibly. Historical `0.4-draft` and
`nf-validation-diagnostics-v1` outputs are not silently treated as this envelope.

## Command Grammar

The accepted forms are:

```text
nexflow validate --root <directory> [--project <relative.yaml> | --file <relative.yaml> ...] [--format text|json]
nexflow inspect  --root <directory> [--project <relative.yaml> | --file <relative.yaml> ...] [--format text|json]
nexflow graph    --root <directory> [--project <relative.yaml> | --file <relative.yaml> ...] [--format text|json]
nexflow --help [--format text|json]
nexflow <validate|inspect|graph> --help [--format text|json]
nexflow --version [--format text|json]
```

`--root` is mandatory for non-informational commands. Source selection modes are
exclusive. With no source flag, require exactly one root `project.yaml` or
`project.yml` and follow only supported Project hints. `--project` selects a
root-relative Project and its hints; repeated `--file` selects only those files,
without following hints. All hinted paths, including those of a nested Project,
are relative to the explicit root. No positional input, stdin, parent search,
recursive scanning, glob, remote/bundle source or configuration discovery exists.

Only `--file` may repeat. `--name=value` and `--name value` are equivalent for
value options. Unknown commands/flags, duplicate singleton options, missing
values, positional arguments, conflicts, and unsupported formats are usage
errors; no fallback or argument-value echo occurs. Help/version are terminal
informational operations and reject conflicting operations/selection options.
`init`, `discover`, `run`, automatic fixes, Mermaid, DOT, SARIF, strict mode,
schema overrides, extension profiles and runtime preflight are unsupported
commands/options in this preview. `init` is deferred, so no command writes files.

## Validation, Inspection And Graph Coverage

Use the [bounded discovery](manifest-discovery.md) rules: an existing explicit
root, regular UTF-8 `.yaml`/`.yml` files, rejection of symlinked roots/components,
root escapes, duplicate source locators/keys, cycles, unknown YAML tags,
non-JSON values and extra YAML documents. Preserve the existing ceilings of
128 sources, 1 MiB per source and 100 alias expansions; callers may lower them.
YAML parsing and schema validation fail closed. Schemas and refs come exclusively
from the pinned package payload; `$id` is not a network fetch instruction.

`validate` covers syntax, discovery association and 17-kind JSON Schema shape.
Whole-project semantic, Core Profile and extension-profile checks are explicitly
`not-run`, even though bounded semantic-fragment library evidence exists. NF-105
must preserve that evidence without advertising fragment success as complete
project coverage. A future semantic expansion requires named rule/fixture and
compatibility evidence, rather than changing what success means silently.

`inspect` runs discovery/schema checks, then returns only allowlisted declared
identities, occurrences and selected unresolved references from
[declared inspection](cli-inspection.md). No raw manifest bodies, secret values,
effective configuration or Agent Assembly are emitted. `graph` derives only the
nodes and selected static edges in [static graphing](cli-graph.md), with explicit
resolved/unresolved/unsupported labels. It does not infer execution ordering,
evaluate approvals, select providers or schedule work. NF-106 must port and
verify these scopes against the real new entry point.

## Output, Failures And Compatibility

Default output is human-readable `text`. JSON mode emits exactly one UTF-8 object
and a final newline on stdout, including usage/internal failures once the entry
point is running; stderr is empty. OS startup/termination, broken pipes and npm
wrapper output are outside this envelope and are never accepted as success.
No command writes report files or writes to its input project.

| Field | Required meaning |
| --- | --- |
| `formatVersion` | Exact `0.5-preview.1`; unknown versions fail consumer validation. |
| `tool` | CLI package identity and actual installed package version. |
| `supportedSpecVersions` | Fixed `["0.1"]`, never copied from unsupported input. |
| `command` | Validated operation, `help`, `version`, or null before command recognition. |
| `success`, `exitCode` | Success exactly when exit code is 0. |
| `inputMode` | One of the three discovery modes, otherwise null. |
| `checks` | Explicit discovery/schema/projection states; semantic/Core/extension/runtime layers remain `not-run`. |
| `executionAuthorized` | Always false. |
| `diagnostics`, `truncated` | Ordered safe diagnostics, at most 200; truncation never changes failure to success. |
| `result` | Bounded successful inventory/inspection/graph or informational result; null on any error. |

NF-106 supplies the concrete output schema/fixtures before claiming these
fields implemented. Diagnostics contain severity, code, safe root-relative file
or null, kind or null, sanitized JSON Pointer or null, safe schema keyword or
null, fixed meaning/message and safe related locations. Preserve reviewed
`NF-DISCOVERY-*`/`NF-SCHEMA` mappings; new CLI-owned usage/internal/limit codes
are `NEXFLOW-CLI-USAGE`, `NEXFLOW-CLI-INTERNAL`, `NEXFLOW-CLI-LIMIT` and must
be documented with fixtures before emission. They are not new standard NF codes.

Sort deterministically by safe file, path, severity, code, schema keyword and
fixed meaning, using code-point lexical comparison, before applying the limit.
Do not echo raw parser excerpts, rejected values, absolute paths, stack traces,
untrusted terminal control characters or native dependency details. Safe authored
IDs/reference locators are permitted only in the allowlisted inspect/graph
projection. A recognized explicit JSON flag selects JSON for usage errors;
flag-like values consumed by another option do not select an output mode.

| Exit | Meaning and precedence after tokenization |
| ---: | --- |
| 0 | Requested bounded operation succeeds, or help/version is returned. |
| 1 | Discovery/input/schema/projection-limit failure. |
| 2 | Invalid usage or unsupported command/flag, including deferred `init`. |
| 3 | Unsupported selected manifest dialect, kind or source hint. |
| 4 | Internal dependency/schema setup failure, incompatible installed package pair or unsupported runtime. |

Usage failures precede workspace reads; an unexpected internal failure precedes
input classifications. Within a completed input assessment, ordinary invalid
input takes precedence over unsupported input when both occur. Failures publish
no partial successful projection. Warnings alone do not imply failure; unrun
checks remain explicit. Consumers require exit 0 and a valid successful envelope,
not a missing/truncated/unparseable response or a successful earlier layer.

## Ownership, Trust And Remaining Work

The existing [NF-101 ownership record](../rfcs/reviews/2026-10-11-single-maintainer-ownership.md)
names Alexander Agafonov for bounded pre-release maintenance, security,
dependencies and release/CI. This profile adds no SLA, backup, on-call, signing
identity or third-party agreement. Both technical review lenses are recorded
under the adopted single-maintainer policy; self-review is not independent
assurance. Separately required release/security assessments remain applicable.

The proposed external-runtime JavaScript/data delivery has no project native
binary to notarize/sign as an app. It must still provide actual source/artifact
hashes, complete notices, reviewed publisher/download route and upstream Node
verification. Checksums are not publisher signatures; unavailable signatures
are disclosed. No foreign key, keychain/OS trust change or protection bypass is
permitted. A future standalone executable reopens native signing requirements.

NF-105 implements the library, NF-106 the CLI, NF-107 actual installable bytes,
NF-108 actual package security/dependencies, NF-109 native lifecycle including
genuine predecessor upgrade/rollback, and NF-110 the candidate-bound release
review. None is passed by this document. No network/provider/credential/tool
execution, executable extension, runtime enforcement or production support is
offered. Published 0.1–0.4 tags and their historical evidence stay unchanged.
