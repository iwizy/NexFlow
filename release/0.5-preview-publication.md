# First Alpha Publication Runbook

Status: prepared, **not authorized or executed**. This runbook applies only to
the exact candidate in [the technical review](0.5-preview-review.md) and its
verified asset inventory. A technical `ready-with-notes` result requests the
maintainer's next decision; it does not create a tag/release permission.

## Authority And Release Cut

1. Obtain a direct instruction identifying the permitted release promotion and
   publication scope. Record the actor, time and exact candidate. Do not infer
   authority from this task, CI, readiness schema, a task merge or a calendar date.
2. Merge the reviewed NF-110 task PR into `develop` after its checks, then open
   the required **`develop` → `main`** release PR. Resolve conflicts forward,
   preserve history and qualify the actual release cut. No task branch enters
   `main` directly. The approved cut must contain both the selected package
   source and the completed review; record their separate immutable revisions.
3. Recheck the exact cut's full relevant source/CI results. Compare `packages`,
   schemas, locks and package-build inputs with selected source
   `89292102783454140671d706c234f8e6d17a337c`. A code/lock/contract change needs
   affected requalification and another readiness decision. Do not silently
   substitute a new merge-commit tarball for the selected native-qualified bytes.
4. Refresh applicable advisory and external-runtime release inputs before
   publication. Changed/unknown inputs stop the transition until reviewed;
   dated qualification results are not a permanent waiver. Preserve affected tool
   versions and bounded dispositions honestly.

The existing `v0.1.0`–`v0.4.0` tags/assets and manifest `specVersion: "0.1"`
remain unchanged. Proposed tag is **`v0.5.0-alpha.1`**, release channel is a
GitHub **prerelease**, and both package versions are `0.5.0-alpha.1`.
Do not label this beta/stable, publish to npm, sign with borrowed keys, or create

## Separate Authorized Publication Phase

Only after the preceding authority and cut checks may the maintainer create
the exact tag and prerelease with the prepared assets. Keep `latest` false so
the current stable milestone is not silently replaced. Upload no credential,
private log, local runtime installation or unrelated file. Verify GitHub's
actual tag target, prerelease/draft/latest flags, asset names and API digests.

Synchronize resulting `main` back into `develop` through the accepted branch
flow without rewriting history, and verify refs/trees. This synchronization is
separate from creating the release; do not combine a version change or next task.

## Public Download And Install Receipt

Download assets afresh from the actual **published prerelease** into a new
directory, using that exact tag rather than a moving branch or prior CI cache.
Verify `SHA256SUMS`, every asset's bytes/digest against the reviewed inventory,
both package provenance/index/schema inventories and the actual tag/cut mapping.
Retain the downloaded originals and raw API identities in the publication receipt.

Repeat [the portable install/quick start](../docs/reference-cli-installation.md)
from those public bytes with the exact external Node/npm route on supported
targets using the [manual public verification workflow](0.5-preview-public-verification.md).
Check real installed help/version, validate/inspect/graph, a rejection,
pure library import and scoped uninstall. Do not reuse a staging install or
mark a target passed without its actual public-byte execution. Existing staged
native records remain valid for their named checks; they do not become public
download observations retroactively.

Record a new publication receipt: direct authority, release-cut/tag/build/review
revisions, CI/native/security inputs, service IDs/timestamps, actual asset names
and hashes, download/install results, failure/withdrawal status, owner and next
action. Update public status only after those facts exist. The current review's
`publicDownloadVerified: false` and historical checkpoints remain original records.

If tag, asset or install results differ, stop the transition, retain the failure
and identify the exact owner/correction or withdrawal action. Never announce
success from an earlier green staging run. Corrections to published bytes need
a separately authorized immutable replacement and clear migration/security notes.
